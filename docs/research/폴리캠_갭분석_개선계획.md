# MOVEVIZ 개선 계획서 — 폴리캠 수준의 정밀 평면도·가구 추출을 향해

> 작성 관점: 프린시플 엔지니어 + 프로덕트 전략. 근거는 (a) 폴리캠/RoomPlan 기술 리서치, (b) 우리 파이프라인 코드 직접 검증(file:line), (c) 적대적 팩트체크 결과를 모두 반영했다. **검증에서 반박·불확실로 판정된 수치는 단정하지 않고 "정성적 방향성"으로만 사용한다.**

## 0. 핵심 한 줄 요약

우리는 **메시를 수평으로 잘라(slice) 히스토그램 합의로 벽을 찾는** 기하 방식을 쓰는데, 폴리캠·RoomPlan·magicplan·Matterport가 정밀한 진짜 이유는 **슬라이싱이 아니라 "점군에서 평면/선을 검출 → 파라메트릭 프리미티브로 피팅 → Manhattan 제약으로 정규화"하는 파이프라인 + 시맨틱 ML**이기 때문이다. 우리 약점의 대부분(가구 시맨틱 부재, 높이/깊이 손실, 벽 위치 ±35cm 누적, 곡선·경사벽 실패)은 이 구조적 차이에서 직접 나온다. 가장 비용효율적인 도약은 **iOS 기기에서 Apple RoomPlan을 도입해 시맨틱 벽/문/창/가구 16종을 온디바이스·무료로 얻고**, 우리 GLB 기하 파이프라인은 RoomPlan이 못 잡는 비-Manhattan·임의 가구 보강용으로 재배치하는 것이다.

## 1. 폴리캠은 어떻게 그렇게 정밀한가 — 캡처 → 평면 → 가구 핵심 메커니즘

### 1.1 캡처: "측정용"과 "비주얼용"은 애초에 다른 트랙이다

리서치의 핵심 통찰은 **정확도 트랙이 둘로 갈린다**는 것이다.

- **측정용 (LiDAR / RoomPlan)**: iPhone Pro LiDAR가 Time-of-Flight로 표면 거리를 직접 측정 → ARKit이 뎁스+포즈(SLAM)를 융합해 실시간 `ARMeshAnchor` 메시 생성. 조명·텍스처 무관, 유효 거리 ~5m. 측량급 LiDAR/포토그래메트리는 ±1~4mm급.
- **비주얼용 (3DGS / 포토그래메트리)**: 사진/영상에서 SfM으로 포즈 추정 후 클라우드에서 가우시안/메시 최적화. "그 자리에 있는 느낌"은 최고지만 **메트릭 정확도와 지오레퍼런싱이 약하다.**

> ⚠️ **팩트체크 주의(반박된 주장)**: 리서치 초안의 "3DGS는 LiDAR 대비 평균 기하 오차 **7.82cm(±11.49cm)**"라는 수치는 **인용된 ScienceDirect 논문(S0926580525005497)에 실제로 존재하지 않으며**, 추적 결과 출처 불명의 벤더 블로그(thefuture3d.com)에서만 나온다. 따라서 **"3DGS는 측정용이 아니라 시각화용"이라는 방향성만 채택하고, 7.82cm라는 구체 숫자는 의사결정 근거로 쓰지 않는다.** (근거: [TU Delft 원문](https://research.tudelft.nl/en/publications/from-comparison-to-integration-a-workflow-evaluation-of-3d-gaussi), [수치 무출처 블로그](https://www.thefuture3d.com/blog/gaussian-splatting-accuracy-guide/))

**→ 우리에게 주는 함의**: 우리 제품(이사 견적·가구 배치)은 **측정용 트랙**에 속한다. 3DGS는 우리 핵심이 아니다. iOS LiDAR로 절대 스케일을 확보하는 우리 방향은 옳다. 단, 정밀도는 LiDAR 트랙 안에서 RoomPlan/기하 파이프라인 품질로 승부해야 한다.

### 1.2 평면: "슬라이싱"이 아니라 "검출 → 피팅 → 정규화"

리서치가 명시한 가장 중요한 사실:

> 정밀 평면도는 **메시를 바닥에서 잘라내는 방식이 아니라**, 점군에서 평면/선을 검출하고 → 파라메트릭 프리미티브(벽=평면, 코너=교점)로 피팅한 뒤 → 직각/Manhattan 제약으로 정규화하는 파이프라인으로 얻어진다.

- **Apple RoomPlan**: 시맨틱 점군을 BEV(조감도) 시맨틱 맵 + Z-slicing 복셀맵(3cm 수평·30cm 수직)으로 투영 → **U-Net 라인 검출 네트워크**가 코너·엣지 맵 출력 → 라인 검증 네트워크가 최종 분류. 문/창은 **벽 평면 위로 정사영한 좌표계**에서 2D 검출. 벽·창 검출 정밀도/재현율 95%, 문 90%, 16종 가구 객체 91%/90% (3D IoU 30% 기준). [Apple ML Research](https://machinelearning.apple.com/research/roomplan)
- **Matterport류**: edge-map 신경망(검출) ↔ line-fitting·polygon heuristics(정규화)를 번갈아 쓰는 하이브리드.

> ⚠️ **팩트체크 정정**: 리서치 초안이 이 파이프라인을 "Matterport Cortex 특허(US 11,551,422)"로 귀속한 것은 **오류다. US11551422는 Apple Inc. 특허**(발명자 Afshin Dehghan 외, 제목 "Floorplan generation based on room scanning")다. 메커니즘 설명 자체는 맞으나 회사 귀속이 뒤바뀌었다. ([Google Patents](https://patents.google.com/patent/US11551422B2/en)) → **결론**: "신경망 검출 + 기하 피팅 + 다각형 정규화 하이브리드"라는 일반 구조는 받아들이되, 특정 특허를 Matterport 근거로 인용하지 않는다.

**정밀도의 실제 출처 3가지** (우리가 채택할 수 있는 부분):
1. **Manhattan-world 정규화**: 모든 벽을 직교 축에 정렬해 노이즈 흡수.
2. **바닥/천장 평면 검출 후 그 사이를 2D 바이너리 맵으로 투영**해 경계 추출.
3. **RANSAC/line-fitting**으로 아웃라이어에 강건한 평면·선 적합.

### 1.3 가구: 시맨틱 인스턴스 + Oriented Bounding Box

폴리캠/RoomPlan의 가구는 단순 occupancy 덩어리가 아니다.

- **RoomPlan 3DOD**: 3D U-Net이 복셀마다 objectness·중심 오프셋·**객체 타입(16종)**·**템플릿 기반 크기**·**빈(bin) 단위 회전(12 bins)**을 예측 → world 축이 아니라 **객체 방향에 정렬된 oriented bounding box(치수+방향)**를 USDZ로 출력.
- **임의 카테고리가 필요하면**: Mask3D(closed-set 20클래스 추론, 24GB GPU 1장), SAM2/OpenMask3D(open-vocab, zero-shot) 같은 공개 모델로 인스턴스 분할 후 **PCA/최소부피 회전박스로 직접 OBB 피팅**.

### 1.4 인디/소형팀의 현실적 재현 경로 (리서치 결론)

| 경로 | 난이도 | 핵심 |
|---|---|---|
| **RoomPlan API 그대로 소비** | 매우 쉬움 | iOS·LiDAR 한정. 무료·온디바이스. 시맨틱 벽/문/창/가구 16종 + 치수를 수십 줄로 |
| **기하 + Manhattan 정규화 자체 구현** | 중하 | RANSAC 평면→2D 투영→반복 RANSAC 선분→Manhattan→다각형. 학습 데이터 거의 불필요 |
| **학습형 평면(FloorNet/CAGE) / 가구(Mask3D)** | 중 | 공개 SOTA + ARKitScenes 파인튜닝. 추론·파인튜닝은 현실적, 처음부터 학습은 비현실적 |

**진짜 해자는 모델이 아니라** 모바일 캡처 UX + 안정적 SLAM/드리프트 보정 + 엣지케이스 휴리스틱(거울/유리/가려진 코너)이다.

## 2. 우리 현재 방식과 구체적 문제점 — 코드 근거와 함께

> 활성 파이프라인은 `02_웹앱_GLB파이프라인/glb-floorplan_1/glb-floorplan/`의 **`glb_to_floorplan.py`(804줄)**, **`glb_furniture_v5.py`(248줄)**, BIM은 `16_bim_export/to_ifc.py`. PLY 파이프라인(`04_1차`)은 노이즈 한계로 사실상 폐기. iOS 앱은 `03_iOS앱/MoveViz-iOS/`. (모든 file:line을 직접 열어 검증 완료)

### 2.1 우리 방식 = "수평 슬라이스 + 합의 히스토그램 + Manhattan 경계"

`glb_to_floorplan.py`의 실제 3단계:

1. **수평 슬라이싱** (`extract_slices`, step=0.2m): 각 슬라이스에서 face normal로 벽면 추출(`abs(fn[1])<0.3`=수직면), 슬라이스당 최대 400점 샘플링.
2. **합의 히스토그램** (`consensus_walls`): 전체 슬라이스 점을 X/Z 1D 히스토그램(bin=0.02m)으로 누적 → `find_peaks`로 벽 위치. presence ratio로 `structure`(r≥0.5)/`built-in`(0.25≤r<0.5)/`noise` 분류 (line 159).
3. **Manhattan 경계** (line 235~): occupancy grid(`RES=0.10`)에 벽 렌더 → **dilate(8)→fill→erode(8)** (line 296,300)로 창틈 ~80cm 자동 브리징 → 최대 연결성분 → 행별 좌/우 경계 추적, 구조벽으로 snap(`snap_tol=0.65`, line 335).

**강점은 진짜다**: 슬라이스별이 아닌 전체 누적이라 울퉁불퉁한 메시 노이즈에 강건하고(`consensus_walls`), dilate+fill로 창/문 갭을 자동 교합하며, presence ratio로 구조벽/가구를 자동 분리한다. 이는 폴리캠의 "기하 + Manhattan 정규화" 경로와 같은 계열이다.

### 2.2 구체적 문제점 (코드 근거)

#### A. 평면 정밀도 — 위치 오차가 누적된다

| 문제 | 코드 근거 | 영향 |
|---|---|---|
| **0.2m 고정 슬라이스** | `extract_slices(... step=0.2)` | 바닥 경사/요철·복층(split-level) 감지 불가 |
| **Normal 필터 오버랩** | `abs(fn[1]) < 0.3` (line 84) | 약 17도까지 기울어진 면도 "수직벽"으로 포함 → 곡선·경사벽 오인 |
| **snap tolerance 과대** | `snap_tol=0.65` (line 335) | 벽이 최대 65cm까지 이동 가능 → 실제 위치 대비 큰 오차 축적, 불규칙 벽은 그리드 각으로 떨어짐 |
| **공격적 평활화** | `median_filter(size=3)` (line 379-380) | 좁은 방(~1.5m)이 그리드 0.1m 기준 ±15cm 변형 가능 |
| **CAD 모드 극단 모폴로지** | `RES=0.05` + `dilate(10)/erode(8)` (line 589,628) | ~1m 브리징 → 인접한 독립 방이 연결될 수 있음 |
| **CAD/LiDAR 자동판정 하드코딩** | `IS_CAD = mesh.faces.shape[0] < 2000` (line 740) | 저폴리곤 LiDAR가 CAD 모드로 오분류 가능 |

#### B. 가구 추출/치수화 — 시맨틱이 없고 높이/깊이가 빈약하다

| 문제 | 코드 근거 | 영향 |
|---|---|---|
| **객체 타입(시맨틱) 전무** | `glb_furniture_v5.py` 반환 dict에 `category`/`class_name` 필드 없음 (line 203-209: bbox/polygon/obb/height_m/footprint_m2/builtin/room_id만) | 침대·소파·옷장 구분 불가. 이사 견적에 치명적 |
| **붙은 가구 과소분할** | watershed가 `area > split_area(1.5㎡)`에서만 작동 (line 159) | 의자 2개(0.32㎡)는 1개로 계산 |
| **빌트인 이진분류만** | `builtin = near_wall and (tall or sides>=2)` (line 196) | "벽 붙은 세탁기 vs 벽 붙은 선반" 구분 불가 |
| **높이 노이즈 민감** | `h = percentile(cell_h, 95)` (line 187) | 쿠션·천장 잡음 1~2점에 높이 과대/과소 추정 |
| **OBB는 있으나 hull 의존** | `_min_area_rect`(convex hull 기반) | 점 분포 비균질 시 회전각 ±5~10도 오차 |

#### C. BIM 출력 — 2D footprint만, 가구·복층 누락

| 문제 | 코드 근거 | 영향 |
|---|---|---|
| **벽 두께 고정** | `THICK = 0.12` (to_ifc.py:13) | 실제 벽 두께 미반영 |
| **단일 층(storey)만** | `IfcBuildingStorey "Level 1"` 하나 (line 36) | 복층·다단계 공간 미지원 |
| **가구가 BIM에 없음** | `to_ifc.py`는 벽/문/창/방(IfcSpace)만 생성, 가구 export 경로 없음 | 추출한 가구가 BIM으로 안 나감 |
| **방=bbox 사각형** | `IfcSpace`를 bbox로만 (line 99-103) | L자형 방 단순화 |

#### D. iOS 의존성 — RoomPlan을 안 쓰고 있다 (가장 큰 미활용 기회)

- 현재 `ScanManager.swift:85`는 `config.sceneReconstruction = .meshWithClassification`, `:279` `ARMeshAnchor` → **원시 메시/PLY export**(`PLYExporter.swift`). **`RoomPlan`/`RoomCaptureView`/`CapturedRoom`을 전혀 사용하지 않는다.** 즉 우리는 Apple이 무료로 주는 시맨틱 벽/문/창/가구 16종 + 치수를 직접 기하 파이프라인으로 재발명하고 있다.
- 메시가 촘촘해 폰 렉 → 다운샘플 후 알고리즘 실행 → 해상도 저하로 미세 개구부·벽 두께 손실(기고문 근거).

### 2.3 우리 검증 수치 (자체 측정, ARKitScenes 60씬)

- 가구 **Recall@0.25 0.145→0.401(2.8배)**, **Recall@0.5 0.051→0.140** (`_대화로그/2026-06-02-v5개선-결과.md`). → **@0.5에서 14%**: 정밀 위치 기준으로는 대부분의 가구를 놓친다.
- 평면 면적비 1.117→**1.087**(과대추정 완화), 단 **벽선·코너 벡터 정확도는 미측정**(ARKitScenes에 벡터 GT 없음, Structured3D 승인 대기).

## 3. 갭 분석 — 폴리캠/RoomPlan vs 우리

| 항목 | 폴리캠·RoomPlan | 우리(현재) | 갭 크기 |
|---|---|---|---|
| **평면 알고리즘** | 점군 평면/선 검출 → 피팅 → Manhattan 정규화 + U-Net 라인검출 | 수평 슬라이스 → 합의 히스토그램 → Manhattan | **중** (계열은 같으나 ML 검출·라인피팅 부재) |
| **벽 위치 정밀도** | RoomPlan 검출 P/R 95%(자기보고). 실측은 벽당 ±5cm 누적 사례 보고 | snap_tol 0.65m, median size=3 → ±15~35cm급 변형 가능 | **중상** |
| **곡선/경사벽** | RoomPlan도 약함(직선화), 폴리캠 Space는 곡면 캡처 | `abs(fn[1])<0.3`로 경사 오인, Manhattan 강제 | **중** (양쪽 다 한계, 단 우리가 더 취약) |
| **가구 시맨틱(타입)** | 16종 분류 + OBB(방향·치수) | **타입 전무**, builtin 이진만 | **상 (가장 큰 갭)** |
| **가구 recall** | RoomPlan 객체 91%/90%(자기보고) | @0.5 14% | **상** |
| **높이/깊이/회전** | OBB 3D 치수 + 12-bin 회전 | 높이 percentile(노이즈민감), OBB는 hull 의존 | **중상** |
| **문/창 검출** | 벽평면 정사영 위 ML 검출 | density=0 갭 검출만 (line 454) | **중** |
| **온디바이스 시맨틱** | RoomPlan 무료·온디바이스 | **미사용**(원시 메시 export) | **상 (즉시 메울 수 있음)** |
| **복층 지원** | (RoomPlan 단층 한계 동일) | 단층(IfcBuildingStorey 1개) | 동률 |
| **BIM 가구 출력** | USDZ에 가구 포함 | 가구 BIM 경로 없음 | **중** |

> 비교 시 주의(팩트체크): RoomPlan 95%/91%/90%는 **Apple 자기보고 "검출 성공률"**이지 "치수 정밀도"가 아니다. 실측 정밀도는 벽당 ±5cm 누적이라는 **단일 사례** 보고가 있을 뿐이다([it-jim](https://www.it-jim.com/blog/roomplan-framework-by-apple/)). "Scaniverse 10.36% vs Polycam 42.58%"는 **1:300 축소 모형의 상대오차**라 실내 공간에 일반화 금지. 즉 **RoomPlan이 만능이라 가정하지 말 것** — 거울/유리/곡면/멀티룸 합성에 약하다.

## 4. 개선 계획 — 항목별 [무엇을 / 왜 / 난이도 / 효과 / 리스크]

### 단기 (4~6주) — "공짜로 얻을 수 있는 것부터"

**S1. iOS에 Apple RoomPlan 도입 (이중 트랙)**
- **무엇을**: `ScanManager.swift`에 `RoomCaptureSession`/`RoomCaptureView`를 추가. 기존 `ARMeshAnchor` 메시 export는 유지하되, RoomPlan의 `CapturedRoom`(벽/문/창/가구 16종 + 치수)을 병행 출력(USDZ/JSON).
- **왜**: 시맨틱 벽/문/창/가구·치수를 **온디바이스·무료**로 즉시 확보. 우리가 코드(`glb_furniture_v5.py`)로 14% recall에 머무는 가구 추출을, Apple 자기보고 90%대 검출로 대체/보완. iOS 앱이 이미 LiDAR·ARKit 기반이라 진입장벽 최소(`sceneReconstruction` 이미 켜져 있음).
- **난이도**: 하 (RoomPlan은 1st-party Swift API, 수십 줄). **효과**: 매우 큼 (가구 시맨틱·문/창·치수 한 번에). **리스크**: iOS+LiDAR 기기 한정, 거울/유리/곡면 약점, 멀티룸 좌표계 합성은 직접 처리 필요. → RoomPlan을 **단일 진실원이 아니라 시맨틱 레이어**로 쓰고, 우리 GLB 기하 결과와 융합.

**S2. 가구에 시맨틱 타입 필드 추가**
- **무엇을**: `glb_furniture_v5.py` 반환 dict에 `category`/`confidence` 추가. 1차로 RoomPlan 카테고리(16종)를 그대로 매핑, RoomPlan 미사용 케이스는 휴리스틱(높이·종횡비·벽접촉) 기반 임시 분류.
- **왜**: 이사 견적은 "소파/냉장고/침대"가 무엇인지 알아야 한다. 현재 타입 필드 자체가 없다.
- **난이도**: 하~중. **효과**: 큼(제품 가치 직결). **리스크**: 휴리스틱 분류 정확도 낮음 → S2를 RoomPlan(S1)과 묶어야 신뢰도 확보.

**S3. snap/평활화 파라미터 정밀화 + 회귀 측정 자동화**
- **무엇을**: `snap_tol=0.65`(line 335)를 적응형(벽 점 밀도 기반)으로, `median_filter(size=3)`를 방 폭 비례로 조정. ARKitScenes dev/test 셋 회귀 스크립트(`13_정확도검증/scripts/score_*`)를 CI화해 파라미터 변경마다 자동 측정.
- **왜**: 현재 ±15~35cm 변형 가능. 측정 없이는 개선 검증 불가(벽 벡터 정확도는 아직 미측정).
- **난이도**: 중. **효과**: 중(정밀도+신뢰). **리스크**: 과적합 → dev/test 봉인 유지.

### 중기 (2~3개월) — "알고리즘 트랙 교체"

**M1. 평면 코어를 "슬라이싱"에서 "평면 검출 → 라인 피팅 → 정규화"로 교체**
- **무엇을**: 메시/점군에서 **RANSAC 평면 분할 → 벽 점 2D 투영 → 반복 RANSAC 선분 적합 → Manhattan 정규화 → 다각형**. 현재 합의 히스토그램은 fallback/검증용으로 격하.
- **왜**: 리서치가 명시한 정밀 평면도의 "정석" 파이프라인. 슬라이싱은 곡선·경사·복층에 구조적으로 취약하다. 외부 학습 데이터 거의 불필요(인디 친화).
- **난이도**: 중. **효과**: 큼(정밀도·강건성). **리스크**: Manhattan 가정은 곡면·예각 방을 못 잡음 → 비-Manhattan은 weak-Manhattan(바닥/천장만 직교)로 완화하고 RoomPlan 결과와 교차검증.

**M2. 가구 인스턴스 세그멘테이션 모델 도입 (RoomPlan 사각지대 보강)**
- **무엇을**: 비-iOS 입력이나 RoomPlan 16종 밖 객체용으로 **Mask3D 추론(closed-set)** 또는 **SAM2/OpenMask3D lifting(open-vocab)** + **PCA/최소부피 OBB 피팅**. ARKitScenes(도메인 일치)로 파인튜닝.
- **왜**: 현재 occupancy+watershed는 붙은 가구·작은 가구에서 recall 14%. 학습형은 추론·파인튜닝이 현실적(처음부터 학습은 비현실적).
- **난이도**: 중. **효과**: 큼(recall·정밀도). **리스크**: GPU 비용·파이프라인 무게 → 추론은 24GB GPU 1장으로 가능, 클라우드 큐로 운영.

**M3. 가구 3D 치수화 정밀화 (높이·깊이·회전)**
- **무엇을**: `percentile(95)` 높이를 robust 추정(MAD 기반 outlier 제거)으로, OBB를 hull 의존에서 **포인트 분포 기반 최소부피 회전박스**로. 깊이(전후) 정보를 슬라이스 점군에서 복원.
- **왜**: 이사 배치엔 좌우뿐 아니라 높이·깊이가 필수(냉장고 문 열림, 선반 여유). 현재 BIM은 2D footprint만.
- **난이도**: 중. **효과**: 중상. **리스크**: 노이즈 민감 → S3 측정셋으로 검증.

### 장기 (3~6개월+) — "통합 제품과 해자"

**L1. RoomPlan(시맨틱) + GLB 기하(정밀 외곽) + 가구 모델 융합 파이프라인**
- **무엇을**: 단일 출력으로 합성. RoomPlan = 문/창/가구 타입, GLB 기하 = 비-Manhattan 외곽·곡면, 가구 모델 = 임의 객체 OBB. 멀티룸 좌표계 정합(RoomPlan 각 스캔 로컬좌표 합성) 직접 구현.
- **왜**: 리서치 결론대로 진짜 해자는 모델이 아니라 **캡처 UX + 강건 SLAM + 엣지케이스 휴리스틱 + 융합/익스포트의 통합**.
- **난이도**: 상. **효과**: 매우 큼(제품 차별화). **리스크**: 통합 복잡도·일관성 — 단계적 융합 + 회귀 측정 필수.

**L2. BIM/Export 확장 — 가구·복층·실측 벽두께**
- **무엇을**: `to_ifc.py`에 가구를 `IfcFurnishingElement`로 추가, 다층(`IfcBuildingStorey` 복수), 벽 두께를 추정값으로(현 `THICK=0.12` 고정 → 측정 기반).
- **왜**: 추출한 가구·복층이 현재 BIM에 안 나간다(반쪽 출력).
- **난이도**: 중. **효과**: 중. **리스크**: 낮음.

**L3. 엣지케이스 강건성 (해자) — 거울/유리·가려진 코너·드리프트 보정**
- **무엇을**: 유리 투과(LiDAR가 유리 뒤를 스캔) 탐지·보정, 가려진 코너 보간, SLAM 드리프트 누적 보정.
- **왜**: 폴리캠/RoomPlan과의 진짜 격차는 정밀도 절대값이 아니라 **강건성·일관성**(리서치 결론).
- **난이도**: 상. **효과**: 큼(신뢰성). **리스크**: 데이터·튜닝 부담 큼 → 가장 마지막.

## 5. 지금 당장 실행할 다음 스텝 3가지 (구체적·측정 가능)

**① RoomPlan 스파이크 (이번 주, ~3일)**
- `ScanManager.swift`에 `RoomCaptureView` 기반 화면 1개 추가, 침실 1곳을 RoomPlan으로 스캔해 `CapturedRoom`을 USDZ+JSON으로 export.
- **측정 가능 기준(Definition of Done)**: 같은 침실에 대해 (a) 우리 GLB 파이프라인 가구 수/타입, (b) RoomPlan 가구 수/타입/치수를 나란히 비교한 표 1장. "RoomPlan이 우리 대비 가구를 몇 개 더, 어떤 타입으로 잡는가"를 숫자로 확인.

**② 벽 벡터 정확도 측정 파이프라인 가동 (이번 주~다음 주)**
- Structured3D 승인 대기 중인 벡터 GT 대신, **RoomPlan의 `CapturedRoom` 벽 좌표를 임시 레퍼런스**로 삼아 우리 `glb_to_floorplan.py` 출력의 코너 위치 오차(평균/95퍼센타일 cm)를 산출하는 스크립트 작성.
- **측정 가능 기준**: 5개 침실에 대해 "우리 코너 vs RoomPlan 코너" 평균 오차(cm)와 최대 오차를 출력. 이 숫자가 S3(snap/median 튜닝)의 베이스라인이 된다. (현재 벽 벡터 정확도는 **미측정** 상태 — 이걸 측정 가능 상태로 만드는 게 최우선)

**③ 가구 dict에 `category` 필드 추가 + RoomPlan 매핑 (다음 주, ~2일)**
- `glb_furniture_v5.py` 반환 스키마에 `category`/`source` 추가하고, RoomPlan 결과가 있으면 그 타입을, 없으면 `unknown`을 채우도록 최소 변경.
- **측정 가능 기준**: ARKitScenes 5씬에서 가구별 타입이 채워진 비율(coverage %)과, RoomPlan 매핑 시 GT 카테고리 대비 일치율(%). 이 수치로 "시맨틱 타입을 RoomPlan에 위임할지, 자체 모델(M2)이 필요한지"를 데이터로 결정.

## 부록 — 의사결정 시 반드시 기억할 팩트체크 단서

| 주장 | 판정 | 행동 |
|---|---|---|
| 3DGS 오차 7.82cm(±11.49cm) | **반박/불확실** (무출처 블로그) | 숫자 인용 금지, "측정용 아님" 방향성만 사용 |
| RoomPlan 검출 95%/91%/90% | **확인** (단 Apple **자기보고 검출률**, 치수 정밀도 아님) | "검출 성공률"로만 표현 |
| RoomPlan 벽당 ±5cm·+37cm | **확인** (단 **단일 사례**) | 일반화 금지, 정성적 한계로 |
| Scaniverse 10.36% vs Polycam 42.58% | **확인** (단 **1:300 축소모형 상대오차**) | 실내 공간 일반화 금지 |
| 평면 파이프라인 특허 = Matterport | **반박** (실제 **Apple** US11551422) | Matterport 특허로 인용 금지 |
| 폴리캠 도면 = RoomPlan API 사용 | **확인** | "폴리캠도 도면은 RoomPlan 래핑" — 우리도 같은 길이 합리적 |

**전략적 결론**: 큰 방향성("측정=LiDAR/RoomPlan, 비주얼=3DGS는 우리 핵심 아님", "인디는 RoomPlan/기하 파이프라인이 현실적")은 견고하다. 우리의 단일 최대 레버리지는 **이미 LiDAR·ARKit를 켜둔 iOS 앱에 RoomPlan을 얹어 시맨틱·치수를 공짜로 얻고**, 자체 GLB 기하 파이프라인은 RoomPlan의 사각지대(비-Manhattan 외곽·임의 가구)를 메우는 보강 트랙으로 재배치하는 것이다.
